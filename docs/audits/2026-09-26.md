# QWarp performance, security, bug, and privacy audit

**Date:** 2026-09-26
**Reviewed baseline:** `6a42da5` on `audit/performance-security-privacy-bugs-2026-09-26`
**Scope:** Application runtime, subprocess and worker boundaries, IPC, settings,
local data handling, desktop integration, dependency constraints, packaging,
and CI/release workflow source.

## Assessment

Four reproducible bugs were fixed without adding features or changing intended
application behavior. The existing audit branch already contained a CI checksum
repair; that earlier work is identified separately below.

No Critical or High application vulnerability was confirmed in this review.
This is a bounded source review and regression-test result, not a security
certification. Remaining findings concern local availability, privacy,
compatibility, and supply-chain hardening. No QWarp telemetry or direct HTTP
client was found. VPN traffic and account enrollment are handled by the official
Cloudflare client and were not audited here.

## Method and limitations

Reviewed the engine, state manager, IPC, main entry point, settings/window/tray,
presentation and asset helpers, platform integration, tests, dependency files,
source archive generation, package metadata, and CI/release workflow source.
Reproduced failures with synthetic inputs and isolated local sockets before
fixing them. Checked the cited Qt advisories against the upstream publications.

Validation used Python 3.14.7, PyQt 6.11.0, and runtime Qt 6.11.2 in the existing
virtual environment, with Qt offscreen. WARP/systemd/polkit calls in affected
paths were mocked. The application was not launched against the host daemon;
no account, tunnel, service, or actual autostart configuration was changed.

Not performed: live VPN/DNS leak testing, desktop/compositor QA, adversarial
multi-process IPC stress testing, independent artifact reproduction, package
installation, a complete CVE database scan, or CPU/RSS/power benchmarking.
Remote CI results and published assets were not reverified in this pass.
Performance conclusions below describe architecture and existing tests, not
measured production latency or memory use.

## Fixed bugs

### BUG-02 — failed notification could remove a live IPC endpoint

**Severity:** Medium, local reliability
**Files:** `src/qwarp/core/instance.py`, `tests/test_instance_and_assets.py`

Previously, any failed notification led to `removeServer()`, including a
successful connection followed by a failed write, an access-denied error, or a
connection timeout. A failed notification does not establish stale ownership.

The notification result now distinguishes success, a potentially stale endpoint,
and uncertain ownership. Uncertain ownership returns `InstanceRole.ERROR`
without removing the socket. Existing missing/refused-endpoint recovery remains.
Tests reproduce write failure, timeout, and access denial and assert that no
unlink occurs. This fixes those paths, **not** the complete ownership race in
SEC-02 below.

### BUG-03 — autostart detection matched comments and unrelated groups

**Severity:** Low
**Files:** `src/qwarp/platform/autostart.py`, `tests/test_platform.py`

A comment or description containing `Hidden=true` incorrectly disabled the UI's
autostart indicator; `Hidden = true` was incorrectly reported enabled. Keys in
other groups also affected the result. Invalid UTF-8 escaped the read-error
handler, causing the combined platform query to fail.

The reader now considers exact keys only in `[Desktop Entry]`, ignores comments,
handles whitespace around assignments, and returns unavailable/disabled on an
encoding error. Boolean values remain case-sensitive. Existing generated files
retain the same behavior. Seven regression cases cover these failures. This is
not a full desktop-environment eligibility evaluator (`OnlyShowIn`, `TryExec`,
etc.). See the [Desktop Entry specification](https://specifications.freedesktop.org/desktop-entry/latest-single/).

### BUG-04 — account diagnostics could raise on numeric or null JSON values

**Severity:** Medium, UI reliability
**Files:** `src/qwarp/ui/settings.py`, `tests/test_ui.py`

Account values passed directly to translation/display code assumed strings.
A numeric quota is not accepted by `tr()`, and a null license reached `len(None)`
in the masking path. These raise in a UI slot instead of updating the dialog.

Account display values are now converted to strings, with null values mapped to
the existing translated `Unknown` placeholder. Numeric zero remains `0`.
Tests cover zero, a positive quota, and null account fields. License masking and
reveal behavior remain covered by the existing tests.

### BUG-05 — fragmented wakeup messages were discarded

**Severity:** Low
**Files:** `src/qwarp/core/instance.py`, `tests/test_instance_and_assets.py`

The server assumed one `readyRead` event contained all six bytes of `WAKEUP`.
It disconnected immediately after a partial read. A real isolated local-socket
test sending `WA` followed by `KEUP` reproduced the missed wakeup.

The receiver now retains valid prefixes, emits one wakeup on completion, and
cleans up the stored prefix on disconnect. The Qt read buffer and each read are
bounded to seven bytes, enough to recognize the command and detect excess data.
The same socket test now passes, as does ordinary primary/secondary startup.

### BUG-01 — earlier CI checksum repair, already present at baseline

**Severity:** Medium, build reliability
**Status:** Existing fix in commit `6b7e638`; unchanged in this pass

Normal CI previously checked a current-tree source archive against the checksum
of an immutable release asset. Post-release source/documentation changes could
therefore fail CI despite correct published metadata. Current CI validates its
artifact bundle against its generated checksums and adjusts Arch checksums only
inside the temporary CI checkout. The stricter release workflow still checks
candidate artifacts against committed release metadata.

The committed `v0.10.0` checksum and release version were preserved. The earlier
report's claims about remote run IDs and published asset digests are historical
evidence, not independently reverified results of this pass.

## Security and robustness findings — report only

### SEC-01 — executable discovery trusts the user's PATH

**Severity:** Low
**Locations:** `core/engine.py`, `platform/taskbar.py`, `platform/autostart.py`

Ordinary commands resolve `warp-cli`, `systemctl`, and the autostart executable
through PATH. A writable earlier PATH directory can shadow them. This requires
control over the launch environment or a trusted executable directory; no shell
injection was found. Privileged service repair resolves its executables from
system locations. Absolute-path validation for all ordinary commands is a
future policy decision because it affects custom installations.

### SEC-02 — IPC ownership is not fully race-proof or explicitly per-user

**Severity:** Low, local availability/reliability
**Location:** `core/instance.py: SingleInstance.acquire`

BUG-02 prevents unlink after known-live or uncertain notification failures.
However, a refused/missing endpoint can be replaced by another contender between
probing and unlinking. The default socket name is also shared rather than
explicitly derived from user identity. Access errors now fail safely, but this
can still prevent startup on a multi-user system.

Qt documents separate access, timeout, and refusal errors; error classification
alone is not an atomic ownership protocol. See [QLocalSocket](https://doc.qt.io/qt-6/qlocalsocket.html).
A per-user ownership lock coordinated with stale-socket recovery requires a
separate design and concurrent-start/mixed-version compatibility testing.

### SEC-04 — accepted IPC connections have no idle deadline or total limit

**Severity:** Low, local resource exhaustion
**Location:** `core/instance.py: _handle_connections`

Accepted peers that never send a complete message or disconnect remain in
`_connections`. Per-peer input is now bounded, but the number and lifetime of
accepted peers are not. A local process able to access the socket could consume
file descriptors and QObject memory. The protocol exposes only window wakeup,
not privileged actions. Consider a short idle deadline and a maximum active
connection count; this review did not choose new connection-policy limits.

### SEC-03 — dependency versions lack artifact hashes

**Severity:** Low
**Locations:** `requirements/ci.txt`, `requirements/release.txt`

Constraints pin versions but do not lock individual wheels/source distributions
with hashes. CI/release still trusts the package index and selected artifacts.
GitHub Actions are SHA-pinned and permissions are scoped per job. Consider
platform-specific hash-locked release inputs; this changes the dependency
maintenance workflow and is report-only.

### ROB-01 — JSON transport trusts parseable output despite a nonzero exit

**Severity:** Informational, compatibility question
**Location:** `core/engine.py: _run_json_command`

A parseable JSON value is returned regardless of exit code. Structured WARP
errors deliberately need this behavior, but an abnormal response containing
success-shaped JSON could be accepted by readers. This was not changed without
establishing the supported CLI contracts: blanket rejection would discard
legitimate structured error states. Future validation should distinguish valid
error/status payloads from incomplete success payloads using captured,
sanitary fixtures from supported clients.

## Privacy findings — report only

### PRIV-01 — observed data flow and existing protections

No analytics SDK, custom HTTP client, or telemetry endpoint was found in the
runtime source. Fixed legal/project links open externally. This does not imply
that the official WARP client or the external browser collects no data.

QSettings persists preferences and a versioned Terms marker, not license keys.
License input is masked; display reveal is explicit; input and cached display
values are cleared on dialog close. Python/Qt memory is not securely erased.
Registration/device/organization details intentionally appear in local settings.
The status JSON endpoint omits the organization name.

Explicit license and organization command arguments are redacted from ordinary
engine logs. CLI error filtering covers common credentials, auth URLs, and
opaque tokens. This is heuristic sanitization, not a guarantee for arbitrary
future error formats. Generic worker/uncaught exception handlers can print
exception messages and filesystem paths to the terminal.

### PRIV-03 — license and organization arguments exist in the child command line

**Severity:** Low, local disclosure
**Location:** `core/engine.py: set_license, register`

The official CLI receives these values as process arguments. Redacting QWarp's
logs does not hide argv from process inspection by observers permitted by the
host's process-access policy. The CLI interface would need a supported stdin or
other secret-input mechanism to avoid this exposure. No such alternative was
assumed, and functionality was preserved.

### PRIV-04 — ordinary logs include network rule targets

**Severity:** Low, local metadata disclosure
**Location:** `core/engine.py: _run_process` and split/fallback actions

INFO command logs include user-supplied split-tunnel IPs, hostnames, and fallback
domains. These are not account credentials but can reveal internal network
names when terminal/journal output is retained or shared. QWarp does not upload
these logs itself. Consider redacting rule values or moving full command detail
to explicitly requested diagnostics; logging policy was left unchanged.

## Performance findings — report only

### PERF-01 — responsive worker architecture with serialization costs

Polling and daemon actions run outside the UI thread. Separate single-worker
query/action/platform pools and pending-query flags limit repeated work. Engine
commands serialize through an RLock, preserving the CLI concurrency contract.
Existing tests cover action/query separation, coalescing, cancellation, and
polling intervals.

Default polling waits are 10 seconds when visible, 30 when hidden, and 1 during
selected transitions, in addition to command execution time. Slow CLI probes or
service repair can delay status and actions behind the shared lock. Most calls
use a two-second timeout; capability/diagnostic probes can use five seconds and
service repair thirty seconds. A multi-command operation can take longer than
one subprocess timeout. No concurrency or polling tuning is recommended without
profiling and client guarantees.

### PERF-02 — bounded workers do not bound all data or shutdown latency

Subprocess output is captured in memory without a byte limit. A faulty CLI can
produce substantial output before a timeout. IPC also retains idle peers as
noted in SEC-04. Shutdown waits for workers on the UI thread and can take longer
than normal operation if commands are slow. These deserve fault-injection and
resource-budget measurements; arbitrary new output/deadline limits could break
legitimate large diagnostics and were not introduced.

### PERF-03 — event-driven icon rendering

SVG pixmaps are regenerated when requested or on theme/state updates. Tiny
bundled assets and event-driven updates give no source-level evidence that an
icon cache is warranted. No CPU or memory saving is claimed; profiling should
precede additional cache state and invalidation logic.

## Dependency and packaging review

The release constraints pin `PyQt6-Qt6==6.11.2`; the local validation runtime
reports the same Qt version. Qt's advisories list 6.11.2 as a fixed version for
[CVE-2026-76151](https://www.qt.io/blog/security-advisory-cve-2026-76151),
[CVE-2026-78253](https://www.qt.io/blog/security-advisory-cve-2026-78253), and
[CVE-2026-19248](https://www.qt.io/blog/security-advisory-cve-2026-19248).
This verifies those three advisories, not the absence of all dependency CVEs.
Native distro packages use the distro's Qt; their patch level was not verified.
The reviewed application does not use a direct HTTP client or QDom parsing and
renders bundled SVGs, reducing exposure to these specific input paths.

Arch metadata depends on `cloudflare-warp-bin` and packages QWarp files only.
CI contains ownership checks and release publication uses a protected
environment, checksums, provenance, master-commit checks, and immutable release
handling. Source review cannot attest to live GitHub environment protection or
credential configuration. No packaging, version, checksum, or workflow changes
were made in this pass.
